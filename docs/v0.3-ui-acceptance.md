# v0.3 UI acceptance — themes, status semantics, countdowns, accessibility

Scope: the visual/product layer shipped for v0.3 — Graphite/Glass/OLED themes,
persisted settings, reset countdowns, provider status semantics, and the
accessibility/viewport hardening pass.

Provenance and RC reconciliation: the evidence below was captured on
`feature/v0.3-ui-hardening` (`7cba0d5`, `8a1c165`) against the pre-prediction
UI based on the released v0.2.1. The release candidate
(`release/v0.3.0-rc`, `505f1b9`) integrated the themes/countdown work
(`3dd6d65`, `6c1f10a`) and rebuilt the status semantics inside
`src/lib/v03Integration.ts`; it did not take the hardening branch's contrast
bump, reduced-motion CSS, or dev scenario harness. Statements are given as
they apply to the RC; branch-only items are marked as such. The prediction UI
added on the RC is covered by `docs/v0.3-product-spec.md` (sections 4 and 8),
`docs/prediction-design.md`, and `docs/human-acceptance-v0.3.0.md` (section 6).

## Supported themes

| Theme    | Selector                     | Surfaces                                                        |
| -------- | ---------------------------- | --------------------------------------------------------------- |
| Graphite | `:root[data-theme="graphite"]` (default, also bare `:root`) | opaque `#1f1f24` cards on `#161619`, no gradient, no blur |
| Glass    | `:root[data-theme="glass"]`  | 55%-alpha cards with `blur(18px) saturate(140%)` over a fixed desktop-like gradient |
| OLED     | `:root[data-theme="oled"]`   | `#060607` cards on `#000`, borders/glow stepped down            |

- Text and accent tokens cascade unchanged across themes; only surfaces vary.
  Readability therefore never depends on the theme.
- The first painted frame is themed: bare `:root` carries Graphite, so there
  is no flash of unstyled content before settings load.
- Theme is persisted in localStorage (`rate-limits.settings.v1`). An unknown
  stored value (e.g. a theme removed later) falls back to Graphite; corrupted
  storage falls back to all defaults. Covered by `src/lib/settings.test.ts`.
- Native Tauri window transparency is intentionally **not** enabled; Glass is
  a CSS-only effect inside an opaque window. Rationale and the WebView2
  details remain in `docs/glass-native-transparency.md` (kept as reference).

## Status semantics (user language)

The status dot alone is color; every non-live state also carries a text note,
and the dot's accessible name uses the same user-language word. On the RC
these rules live in `src/lib/v03Integration.ts`
(`providerStatusPresentation` / `providerSourceNote`, unit-tested in
`src/lib/v03Integration.test.ts`); the hardening branch had them in
`src/lib/status.ts`, which the RC does not contain.

| State          | Dot    | Note                                                            | Meaning |
| -------------- | ------ | --------------------------------------------------------------- | ------- |
| Live           | green  | `Checked 14:32`                                                  | Provider returned fresh data successfully (direct API fetch) |
| Cached         | green  | `Source updated 12m ago` (dim)                                   | Data comes from a provider cache/source (Antigravity quota cache) and is inside the freshness threshold. Deliberately **not** visually identical to Live |
| Stale          | amber  | `Showing data from 08:10` or `Source update time unknown`        | The known source timestamp is beyond the accepted freshness threshold (Antigravity: 24h) |
| Refresh failed | red    | with retained values: `Showing last good data from 42m ago`; without: `No saved provider data` | The current refresh failed; previous usable values are kept but are explicitly dated so they can never read as current |
| Unknown        | gray   | `Data source unknown`                                            | Provider responded but returned no usable windows |
| Mock           | —      | `Deterministic sample data`                                      | Simulated provider card (Claude, xAI Grok) |

RC differences from the hardening-branch wording: the no-usable-windows state
is labeled `Unknown` / `Data source unknown` (the branch draft called it
`No data` / `No usage data from this provider yet`), and Mock is a first-class
presentation because the RC renders Claude and xAI Grok as permanent mock
cards.

Rules (unit-tested on the RC):

- Stale ≠ error: stale means "data is old but that's the source's truth";
  error means "our refresh failed".
- Retained last-good values after a failure keep their original fetch time
  and the note dates them.
- Cached-fresh data never reads as Live (distinct note, and the accessible
  name says "Cached").
- The header subtitle names the data source classes:
  `Codex, Z.ai, OpenCode Go & Antigravity live · others mocked`.
- Labels are applied where they carry meaning; live cards stay clean. The
  labels are not sprinkled mechanically.

## Countdown behavior

`formatCountdown` / `formatResetLine` (`src/lib/format.ts`, unit-tested in
`src/lib/format.test.ts`):

- Resolution: `>7 days` → absolute date only (`Resets Oct 19 · in 21d 4h`);
  `1–7 days` → weekday + time (`Resets Thu 7:53 AM · in 3d 0h`); same day →
  time only (`Resets 12:53 PM · in 5h 0m`).
- Granularity: `5d 13h` → `2h 17m` → `18m` → `<1m`. Truncated, never
  overstated; zero-padding kept on exact boundaries (`1d 0h`, `2h 0m`).
- Exactly at the reset instant and past it: `Reset time passed` — retained
  (no negative countdown). A future-dated stamp cannot produce a negative
  age either.
- Missing `resetAt` → no reset line at all. Invalid timestamp → the line is
  omitted (empty string), never "Invalid Date" or a thrown error.
- Timezone/DST: all reads use the user's locale via `Intl`; the day/hour
  countdown split is computed from elapsed milliseconds, so a DST shift
  inside the span cannot change the readout (regression-tested).
- Countdowns tick from a local 30-second `useNow` wall clock. Providers are
  **not** fetched more often for countdowns.

## Accessibility

- Keyboard: the refresh button, both selects, the startup switch, and the
  `Clear history` button (added on the RC) are the tabbable controls. The
  shared `:focus-visible` rule gives each a visible outline; on the RC the
  prediction block is also focusable and reveals its basis tooltip
  (`.prediction:focus-visible`). The dedicated guardrail test for
  `:focus-visible` lives on `feature/v0.3-ui-hardening`
  (`src/themeCss.test.ts` there) and is not part of the RC's test file;
  interactive keyboard verification still needs the manual Tauri smoke test
  recorded in `docs/human-acceptance-v0.3.0.md`.
- Status is not color-only: every non-live state has a text note plus an
  accessible name (`role="status"`).
- Usage bars are `role="progressbar"` with `aria-label`, `aria-valuenow/min/max`.
- Refresh button has `aria-label="Refresh"`; the startup control is a labelled
  `role="switch"`; both selects are labelled by their visible row labels.
- Contrast: the hardening pass bumped the faintest text tier from `#71717c`
  (3.4:1 on Graphite cards at 10.5px) to `#8a8a95` (≥4.8:1 on all three
  themes). **Not carried into the RC:** `release/v0.3.0-rc` still ships
  `--text-faint: #71717c`; the bump is recorded here as accepted follow-up
  work, not as shipped RC behavior.
- `prefers-reduced-transparency: reduce` and missing `backdrop-filter`
  support both switch Glass to opaque cards (`@supports` + media-query
  fallbacks; guardrail-tested on the RC in `src/themeCss.test.ts`).
- `prefers-reduced-motion: reduce` disabling the refresh spinner and
  usage-bar transitions was part of the hardening pass but is **not** in the
  RC; recorded here as accepted follow-up work.

## Viewport / scaling checks

Inspected at 400 × 760 and 360 px minimum width (the tray window size,
`minWidth: 360` in `src-tauri/tauri.conf.json`), across all three themes and
the scenario set below. The RC adds the prediction block inside window rows;
the same no-overflow expectation for it is covered by the RC acceptance
criteria and `docs/human-acceptance-v0.3.0.md`.

- No horizontal overflow at 360 px (`scrollWidth == clientWidth == 360`).
- Long provider names and long window labels wrap instead of pushing the
  percentage or status dot around; the percentage never shrinks.
- The reset line is nowrap + ellipsis, right-aligned, so a long locale
  rendering cannot overflow the card.
- Settings rows, footer, and scrollbar remain usable at both widths.
- 125% Windows scaling: the layout is fixed-CSS-pixel based with no
  viewport-relative units; WebView2 scales it uniformly, so no separate
  layout risk beyond font metrics. (Verified conceptually; not a native
  DPI run.)

States inspected per theme: normal mix, high usage (85–100%, critical tone),
all-100%, stale, refresh-failed with retained values, refresh-failed empty,
no-data, long provider/window names, far-future reset (>7d date-only), empty
provider list ("Loading…"), settings always-visible panel, startup toggle
disabled state.

### QA harness

Branch-only: **not part of the RC.** On `feature/v0.3-ui-hardening`,
`?uiScenario=normal|high|maxed|mixed|long|empty` (dev builds only, wired in
`src/main.tsx` via a DEV-guarded dynamic import of `src/dev/uiScenario.ts`)
staged provider states that need backend data, and production bundles
excluded the module. The RC contains no `src/dev/` harness; equivalent

## Known cosmetic limitations

- Relative-age notes ("Source updated 42m ago") are computed against a
  30-second local tick. If a refresh lands within a few seconds of a d/h/m
  unit boundary, the first paint after that refresh can read one unit low
  until the next tick (≤30 s). Self-correcting; data is never wrong, only
  the rounding of an age that sits on a knife edge.
- Countdowns beyond ~99 days read `in 366d 0h`. No current provider resets
  further out than ~35 days; treated as acceptable rather than adding a
  display cap.
- The refresh spinner could not be captured (scripted providers resolve
  instantly); its disabled + spinning states come from the imported,
  previously reviewed implementation.
- Status-dot color pairs (green vs amber) also differ by note text, but two
  adjacent live cards are only distinguishable by name — by design.

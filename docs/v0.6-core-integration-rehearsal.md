### Base decision

**`release/v0.5.0-rc` (`34bf0e4`)**, not `feature/v0.6-production-updater`:

- It is the newest **shared ancestor** of all seven lanes (every lane's
  merge-base with it is one of its own ancestors).
- Two lanes (status-contract, history-trends) sit directly on it — they
  replay with zero replay of anything else.
- Every other lane replays only its own commits; the commits between the
  older lane bases and the release head (main-window redesign, LimitScope
  brand, v0.5.0 version bump, installer migration fix) are already in the
  base and are not re-replayed.
- `feature/v0.6-production-updater` as a base would *drop* `6cda2d3`
  (installer migration fix) and `34bf0e4` (release acceptance records),
  regress the base, and still require replaying the status-contract and
  history lanes.

### Integration order and why

Cherry-picked order (each lane's commits in order):

1. **runtime-status-contract** — applies cleanly on the release head and
   defines the canonical `ProviderHealth` vocabulary with `set_health()` as
   the single write point. Every later lane's status handling must adapt to
   it, never the reverse, so it lands first.
2. **history-trends** — also sits directly on the release head; only overlap
   with (1) is ~20 lines of `history.rs` (auto-merged) and one guardrail
   test line.
3. **persisted-last-good** — hydration must express itself through the new
   canonical health, so it follows (1). Its `runtime.rs` surface is small
   (+37) and auto-merged.
4. **notification-recovery** — the recovery policy must gate on the
   canonical health, so it follows (1); lands before diagnostics so the
   diagnostics lane's small `notifications.rs` addition lands on the final
   policy shape.
5. **redacted-diagnostics** — consumes the runtime's failure/success state
   (its `last_failures`/`last_successes` instrumentation) and projects the
   canonical health, so it follows (1)–(4). Its `App.tsx`/`styles.css`/
   Cargo conflicts with the updater lane are taken here so the updater lane
   lands last on the frontend side.
6. **production-updater** — mostly frontend/packaging; must precede (7)
   because provider-correctness is a direct git descendant of the updater
   head.
7. **provider-correctness** — last. Its `runtime.rs` changes center on the
   failure projection that (1) rewrote and (5) instrumented; resolving it
   last means its intent (the account-identity guard) is re-expressed once,
   against the final shape of that function.

This matches the dependency direction in the rehearsal brief except for one
inversion the brief itself anticipated: the brief listed provider-correctness
third and production-updater last, but the git lineage has
provider-correctness stacked on production-updater, so the updater lane must
land first.

## Conflicts encountered and resolutions

Git conflicts (explicit markers):

1. **`cooldown_skip_dto` (runtime.rs)** — status-contract overlays canonical
   `Cooldown` health on the failure projection; diagnostics projects with
   the failure's *original* timestamp (`apply_failure_at`) so the redacted
   diagnostics timeline shows when the refresh actually failed. **Both kept:**
   project via `apply_failure_at(kind, failure, cooldown.failure_at)` and
   overlay `set_health(&mut dto, Cooldown)` afterwards.
2. **`apply_failure_at` (runtime.rs)** — status-contract computes normalized
   error metadata (`error_category`, `error_http_status`); diagnostics
   records `(failure, failure_at)` into `last_failures` for the redacted
   diagnostics source. **Both kept** — neither subsumes the other.
3. **failure projection retention path (runtime.rs)** — the central semantic
   conflict: provider-correctness's account-identity guard rewrites the same
   retained-last-good block that status-contract re-expressed through
   `set_health`. **Resolution:** the identity guard decides *whether*
   retention happens; the canonical contract decides *how* a retained entry
   is presented (`set_health(Error)` + error metadata). An account mismatch
   falls through to the bare `unavailable`/`error` entry exactly as lane 7
   intends.
4. **`Cargo.toml` / `main.rs` / `App.tsx` (updater vs diagnostics)** — both
   lanes add dependencies/plugins/settings-drawer sections at the same
   anchor points. **Both kept** (regex + updater/process plugins; dialog +
   process + updater plugins; diagnostics row + UpdatesSection).
5. **`state/project-state.md` (twice)** — the diagnostics lane's state doc
   was written against its older, pre-rename, pre-v0.5-RC lineage. Kept the
   current v0.5.0-RC reality, folded in the diagnostics capability
   description (no longer "isolated"), dropped the superseded v0.4-era
   sections, and updated the "not integrated" truth to reflect the rehearsal.

Silent semantic conflicts (clean auto-merges that did not compile or did not
behave — the reason this rehearsal exists):

6. **Hydration vs canonical health (compile error, E0063).** `last_good.rs`
   built hydrated DTOs with the legacy `status: "stale"` string only and
   gated `record_success` on `status == "ok"`, predating the `health` field.
   **Resolution:** hydration carries `health: Stale` with the legacy string
   derived from the same enum value; write eligibility gates on
   `health == Live`. Lane tests pin canonical health alongside the legacy
   projection.
7. **Diagnostics fallback health (compile error, E0308).**
   `diagnostic_source()`'s no-usage fallback passed the legacy `"unknown"`
   string to `base_usage`. **Resolution:** `ProviderHealth::Unknown`.
8. **Cross-lane test fixtures (compile errors).** Diagnostics' test DTO and
   runtime/last_good `ProviderFailure` fixtures predated the
   `health`/`error_category`/`error_http_status`/`identity` fields. **Fix:**
   fixtures extended; assertions strengthened where they pinned health.
9. **Recovery cooldown fixture (behavioral test failure).**
   `recovery_cooldown_retained_does_not_notify` built a DTO with
   `status: "error"` but `health: Live` — an impossible state under the
   canonical contract (status is derived). The shared eligibility gate now
   reads canonical health, so the invalid fixture passed eligibility and
   fired a recovery notification. **Fix:** the fixture builds the real
   cooldown projection (`health: Cooldown`, derived status); the assertion
   (no notification) is unchanged and passes.
10. **Merged-away React import (behavioral).** The diagnostics lane's
    `useCallback` import lost the auto-merge against the updater lane's
    `App.tsx`, breaking every App render test. **Fix:** import restored.
11. **Brand guardrail (behavioral).** The diagnostics lane's test fixture
    carried the pre-rename product name "Rate Limits". **Fix:** fixture
    rebranded to LimitScope (identifier `com.ratelimits.desktop`
    intentionally unchanged).

Contract-completing integration change (not a conflict, a gap):

12. **Diagnostics canonical health serialization.** The diagnostics lane
    serialized only the legacy `status` string. Per the rehearsal contract
    ("normalized runtime status should use the canonical health contract"),
    the bundle now carries `health` (canonical enum word) alongside the
    derived `status`; the schema test pins both and their agreement, and
    `docs/diagnostics-contract.md` documents the field.

## Runtime health, persisted last-good, and semantic contracts

- Canonical health remains Rust-owned: `live`, `stale`, `unknown`,
  `cooldown`, `error`, `unavailable`. The legacy `status` string survives
  only as the derived wire projection (`legacy_status()`), written through
  the single `set_health()` point.
- Cold-start hydration: `health = stale`, `freshness = stale`, never live,
  no history samples, no history revision movement, no notifications,
  expired `resetAt` windows dropped (never a fake future reset), 7-day
  bounded cache age, account isolation preserved.
- Provider correctness: Antigravity fetches live Google quota first with the
  plugin cache as offline fallback and never fabricates freshness;
  OpenCode Go drops retained last-good across an account change (identity
  guard); OpenCodex private credentials are never a production source.
- History: 24h detailed tier + 7d bounded compacted tier, reset boundaries
  preserved across compaction, prediction queries strictly dense-24h and
  isolated from compacted data, only live-eligible observations record.
- Notifications: near-limit/critical/recovery evaluate only
  live-eligible observations; stale, persisted last-good, cooldown, error,
  unavailable, unknown never notify; recovery stays tied to genuine forward
  reset-cycle progression with a proven previous peak.
- Diagnostics: no raw provider response text, no tokens, no authorization
  material, no email/JWT/sk-* shapes; bounded sanitization; the bundle now
  carries the canonical health word.
- Updater: configured public feed URL, public key, startup/manual update
  flow, NSIS passive mode, and release workflow assumptions all verified
  intact after the merge; nothing published.
